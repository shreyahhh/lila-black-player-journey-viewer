LILA BLACK Player Journey Viewer

XCoordinated

A browser-based tool for the Level Design team to explore how players actually move, fight, loot, and die across LILA BLACK's three maps - built from 5 days of real production telemetry.

1,243 Parquet files · 796 matches · 89,104 events · 3 maps · 5 days (Feb 2026)

The dataset

AmbroseValley, GrandRift, Lockdown - human and bot players, Feb 10–14 2026.

The goal

Turn raw telemetry into something a Level Designer can open and use: no queries, no notebooks.

Coordinate Mapping

The assignment's own README calls this "the tricky part." It was verified against the real dataset, not just implemented from the spec.

u = (x - origin_x) / scale
v = (z - origin_z) / scale
pixel_x = u * image_width
pixel_y = (1 - v) * image_height   // Y flip: world Z vs. image top-left origin
  • Verified. 100% of transformed points land inside image bounds, across all 89,104 rows and all 3 maps.
  • Found. Minimaps are not 1024×1024 as documented - real sizes read at runtime instead (4320×4320, 9000×9000, and a non-square 2160×2158).
  • Verified. Visually validated: paths trace roads and hug buildings correctly on every map.

Data Pipeline

Everything risky happens once, offline, in Python: the browser only ever sees plain pixel coordinates and JSON.

1,243 Parquet files (89,104 rows, 796 matches, 3 maps, 5 days)
        │  pipeline/preprocess.py
        ▼
796 match JSON files + index.json + 3 per-map _aggregate.json  (~6.6MB)
        │  viewer.html (fetch)
        ▼
Rendered in-browser: paths, event markers, heatmaps, playback
Data quirk

The ts column is typed timestamp[ms], but the raw values are actually Unix-epoch seconds. Decoding as milliseconds gives a nonsense 1970 date, while seconds land on real dates inside the dataset's actual Feb 2026 window. Full list of nuances found is on the Assumptions & Data Issues page.

Assumptions & Data Issues

Every real gotcha found in the raw dataset, and exactly how it was handled - not just the one called out on the Data Pipeline page.

IssueWhat was foundHow handled
Minimap sizeREADME says 1024×1024; real files are far larger, and GrandRift isn't even squareRead actual image dimensions at runtime with Pillow, never hardcode 1024
ts columnTyped timestamp[ms], README calls it "match-relative" - neither is right. The raw int64, decoded as epoch seconds, lands on real Feb 2026 dates; decoded as milliseconds it lands on 1970Read the raw int64 as epoch seconds, then convert to match-relative seconds for playback
Human/bot detectionEvent name (Position vs. BotPosition) is unreliable - bot IDs were found emitting plain Position/Loot eventsClassify strictly by user_id format (UUID vs. numeric), ignore event-name prefixes
Multiple maps per matchVerified 0 matches reference more than one map_idGrouping by match_id alone is safe - no special handling needed
Missing/garbled rows0 nulls, 0 NaN/Inf across all 89,104 rows; all 1,243 files parsed without errorNo filtering/cleanup step needed beyond decoding event bytes
Sparse player files4 matches have a player file with only 2 rows total - real telemetry gaps, not corrupt dataRendered as-is; a future dataset with larger gaps would need a "teleport" gap-detection heuristic
Events with no matching fileSome matches reference an actor (e.g. a BotKilled) with no position file present for it in that matchOnly renders players/bots with an explicit position file - never fabricates a path for data that doesn't exist

Tradeoffs

Every major decision, and the alternative it was weighed against.

DecisionAlternative consideredWhy this way
Preprocess to static JSON, no backendIn-browser Parquet parsing (DuckDB-Wasm)Isolates the risky coordinate/ts/bot-detection logic in one debuggable script; keeps the frontend trivially simple and hosting free
Leaflet + CRS.Simpledeck.glLighter-weight, most direct precedent for this exact problem; deck.gl's WebGL headroom isn't needed at this data scale (≤ a few thousand points/match)
One JSON file per matchOne giant JSON for all matchesKeeps initial page load small - a Level Designer only ever looks at one match at a time

Getting Started

Everything needed to run this locally or regenerate the data from scratch.

Setup

python -m venv .venv
source .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install pyarrow pillow

# Regenerate data/ from the raw parquet files
cd pipeline
python preprocess.py --src "<path to player_data/player_data>" --out "../data"

Running locally

# from the repo root
python -m http.server 8000
# http://localhost:8000/            -> landing page
# http://localhost:8000/viewer.html -> the tool directly
# http://localhost:8000/docs.html   -> documentation

A plain file:// open won't work - the viewer fetch()s JSON, which needs to be served over HTTP.

Deploying

100% static - drag the repo root onto Vercel/Netlify, or serve via GitHub Pages (Settings → Pages → deploy from main / root). No build step, no environment variables, no config.

Scope

LILA Games' Level Design team has raw player telemetry but no visual way to answer basic design questions - where players fight, where they die to the storm, which parts of a map never get visited.

The user

A Level Designer - not a data scientist. They think in terms of "this building," "that choke point," not x=1099.5, z=2963.8.

The job

Open a match, watch it play out on the real map art, and spot patterns - in one match, or across hundreds.

Non-goals for this pass

  • Real-time/live telemetry: this is a historical-data explorer, not a live dashboard
  • Cross-map or cross-day comparison views (e.g. AmbroseValley vs. Lockdown side by side)
  • Authentication/access control: user_id is an opaque UUID/bot-id with no PII, so an open link is fine for this exercise
  • Editing or annotating the data from the tool - it's a read-only viewer

Product Decisions

Why the tool behaves the way it does.

  • Match dropdown sorted by player count: surfaces the busiest, most likely-interesting matches first
  • Heatmap defaults to "off": a heatmap over a path-covered map is noisy as a default view
  • Map-wide heatmaps are precomputed at build time, not fetched live: a single match has too few kill/death events to show a real pattern
  • Playback defaults to 2×: matches run up to ~15 minutes; real-time is tedious for a first look
  • No login, no per-user state: nothing in the requirements calls for it over already-anonymized data

Data Insights

Four things the data revealed, each backed by a real stat and an actionable read for the design team. Full writeup in INSIGHTS.md.

Map rotation is heavily skewed - 71% AmbroseValley

566 of 796 matches (71%) are on AmbroseValley; Lockdown gets 171 (21%); GrandRift just 59 (7%) - an order of magnitude less playtesting signal than the other two. If rotation is meant to be roughly even, this is worth a look at matchmaking weight config.

PvP is nearly absent - ~0.1% of combat

Only 3 human-on-human kills across all 796 matches, vs. 2,415 bot kills - holds per-map too. If human PvP tension is meant to be part of the appeal, players are almost never actually encountering each other.

Storm rarely kills - ~5% of matches

39 storm deaths total. Lockdown's rate (~10%) is roughly double AmbroseValley's (~3%) despite being the smaller, closer-quarters map - if storm pressure should be a bigger late-match forcing function, Lockdown is the one to tighten first.

Loot density is lower on Lockdown - ~12 vs. ~15-18/match

Lockdown averages ~12 loot pickups/match vs. ~17.6 on AmbroseValley and ~14.9 on GrandRift, despite similar match durations (~400-430s) - worth checking loot spawn density with the heatmap now that it's live.

Production Considerations

This was built as a static, read-only tool over a fixed data snapshot - the right scope for the assignment, not how a permanent tool would be built. What changes if LILA Games kept this running against live data:

ConcernCurrent approachIn production
Data freshnessOne-time snapshot → static JSONA scheduled ingestion job re-running the same pipeline against new match data
Data volume6.6MB total, fits in a git repoA real datastore (Postgres/DuckDB) + pagination instead of one index.json listing every match
HostingGitHub Pages (free, rebuilds need a commit)Any standard static host behind the company's auth, likely SSO-gated
Access controlNone - no PII in the dataSSO-gated access if tied to real accounts in the future
Schema driftHardcoded per-map scale/origin, validated oncePipeline should validate its own assumptions on every run (see Roadmap)
ObservabilityNone - offline script, run manuallyIngestion failures should alert someone rather than fail silently

Roadmap

This was scoped correctly for a fixed 5-day data snapshot. Full production considerations are covered separately. Near-term next steps:

  1. Automated pipeline validation (assert points stay in bounds, human/bot counts reconcile) so a future data refresh can't silently break coordinate mapping
  2. Point the insights at exact map locations now that the heatmap is live
  3. Per-(map, date) aggregate heatmaps, if "has traffic changed over the 5 days" becomes a real question
  4. Minimap image compression: Lockdown's JPG and AmbroseValley's PNG are several MB at full resolution - fine here, but worth a build-time downscale pass if load time on a slow connection becomes a concern
