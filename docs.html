XCoordinated

LILA BLACK Player Journey Viewer

A browser-based tool for the Level Design team to explore how players actually move, fight, loot, and die across LILA BLACK's three maps, built from 5 days of real production telemetry (796 matches, 89,104 events).

The dataset

1,243 Parquet files · 3 maps (AmbroseValley, GrandRift, Lockdown) · Feb 10–14 2026 · human & bot players.

The goal

Turn raw telemetry into something a Level Designer can open and use: no queries, no notebooks.

Tech Stack

No framework, no build step: a static site is the whole product.

Coordinate Mapping

The assignment's own README calls this "the tricky part." It was verified against the real dataset, not just implemented from the spec.

u = (x - origin_x) / scale
v = (z - origin_z) / scale
pixel_x = u * image_width
pixel_y = (1 - v) * image_height   // Y flip: world Z vs. image top-left origin
  • 100% of transformed points land inside image bounds, across all 89,104 rows and all 3 maps
  • Minimaps are not 1024×1024 as documented; real sizes read at runtime instead (4320×4320, 9000×9000, and a non-square 2160×2158)
  • Visually validated: paths trace roads and hug buildings correctly on every map

Data Pipeline

Everything risky happens once, offline, in Python: the browser only ever sees plain pixel coordinates and JSON.

1,243 Parquet files (89,104 rows, 796 matches, 3 maps, 5 days)
        │  pipeline/preprocess.py
        ▼
796 match JSON files + index.json + 3 per-map _aggregate.json  (~6.6MB)
        │  viewer.html (fetch)
        ▼
Rendered in-browser: paths, event markers, heatmaps, playback
Also found: the ts column is typed timestamp[ms] but the raw values are actually Unix-epoch seconds. Decoding as milliseconds gives a nonsense 1970 date, while seconds land on real dates inside the dataset's actual Feb 2026 window. See ARCHITECTURE.md for the full list of data nuances found.

Product Decisions

Why the tool behaves the way it does.

  • Match dropdown sorted by player count: surfaces the busiest, most likely-interesting matches first
  • Heatmap defaults to "off": a heatmap over a path-covered map is noisy as a default view
  • Map-wide heatmaps are precomputed at build time, not fetched live: a single match has too few kill/death events to show a real pattern
  • Playback defaults to 2x: matches run up to ~15 minutes; real-time is tedious for a first look

Data Insights

Three things the data revealed, each backed by a real stat. Full writeup in INSIGHTS.md.

Map rotation is skewed

AmbroseValley: 71% of matches. GrandRift: just 7%, an order of magnitude less playtesting signal than the other maps.

PvP is nearly absent

Human-vs-human kills are ~0.1% of all combat events; almost all fighting is against bots.

Storm rarely kills

Only ~5% of matches have any storm death: the late-game pressure is coming from somewhere else.

Roadmap: if this became a permanent tool

This was scoped correctly for a fixed 5-day data snapshot. Full production considerations (data freshness, access control, observability) are in DOCS.md. Near-term next steps:

  • Automated pipeline validation (assert points stay in bounds, human/bot counts reconcile) so a future data refresh can't silently break coordinate mapping
  • Point the insights at exact map locations now that the heatmap is live
  • Per-(map, date) aggregate heatmaps, if "has traffic changed over the 5 days" becomes a real question
